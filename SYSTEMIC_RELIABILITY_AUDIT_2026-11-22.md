# Chess Buddy and VBOT Studio reliability audit

**November 22, 2026 · `add-llm-log` · `5feee1c6dbd4b65513b1f0945c70f70e5b153721`**

Two findings warrant release holds. The direct-drive helper can acknowledge a stop while an older velocity publication is still in flight. A fresh deployment from the checked-in Dockerfile cannot start the chess backend. Ten further findings affect unattended robot dispatch, Android ownership and pairing, live chess, access control, and saved work.

Critical means a stop guarantee fails or an entire supported deployment cannot start. High means a supported workflow can fail completely, an operator can lose control of its lifecycle, or persisted work or service authority is at risk under the stated conditions. Severity describes impact. Each finding identifies the evidence and the conditions separately.

## Critical findings

### C1. Direct drive can publish movement after acknowledging Stop

The watchdog copies the active command under a lock and publishes it after releasing that lock. The input thread can end the drive concurrently, publish the stop burst, remove the unresolved-action marker, and acknowledge success. In the existing drive harness with a delayed fake publisher, the completion order was five zeros followed by the older nonzero frame. The acknowledgement reported `zeroed=true`. Actual actuator behavior depends on the downstream controller. This test used an in-memory publisher. [Dog-side drive helper](vbot-demo/robot_studio.py#L307)

**Reinforcement.** Give velocity output one ordered writer. Stop must invalidate pending movement and acknowledge only after earlier publications have completed and the final zeros have been issued. If the publisher cannot confirm that ordering within a deadline, preserve the unresolved marker and report an unknown outcome. Gate direct-drive promotion on a delayed-publisher regression and subsequent supervised hardware acceptance.

### C2. The repository Dockerfile builds a backend that exits before listening

The image copies three application directories. Importing the HTTP handler imports the robot demo, which imports the capture lessons and synchronously reads `src/captureExercises.json`. Staging exactly the application files copied by the Dockerfile produced `FileNotFoundError` before server startup. Adding just the catalog in the temporary staging tree restored the import and a real Stockfish search returned a legal move. The image also omits the HTML that the local VBOT console route reads. A deployment with additional mounts or a different image can behave differently. [Dockerfile](Dockerfile#L13) · [Catalog loader](server/capture_practice.py#L7) · [VBOT console route](server/app.py#L1701)

**Reinforcement.** Package the catalog and supported console assets explicitly. CI should boot the built image with clean storage, query readiness and analyze a known position. For a robot-enabled image, verify the SSH client, host-key tooling and required mounts inside that same image. The audit exercised the copy layout with host Python and Stockfish. A Linux container build and a running production image were outside that verification.

## High findings

| ID | Failure and evidence | Reinforcement and acceptance check |
| --- | --- | --- |
| H1 | **A victory can trigger motion after the supervising device goes offline.** The win worker dispatches through a path that checks arming, generation and robot identity but omits operator freshness. With a 15-second lease, 16 seconds after the last check-in, the canonical game-end observer called the fake motion sender once. The ordinary move and performance paths have separate presence checks. [Victory dispatch](server/vbot_demo.py#L730) · [Shared sender](server/vbot_demo.py#L984) | Check the arming session’s operator lease at the final dispatch boundary for every motion tier, including after a cooldown. Bind renewal to the supervising session so a second status viewer cannot keep it alive. Require zero sends after expiry in both immediate and delayed victory cases. |
| H2 | **Android’s “Stop backend” can leave the controller armed and a show uncancelled.** The notification stops the foreground service. Python supplies only a shutdown reason to a disarm method that rejects scoped requests without a matching game and generation. Running the Android stop function against the real controller with fake I/O left `armed=true` and the cancellation event unset. The worker can survive in the Android process after the HTTP listener closes. [Service shutdown](android/app/src/main/java/com/andy/chessbuddy/StandaloneService.java#L48) · [Python shutdown](android/app/src/main/python/android_backend.py#L111) · [Disarm guard](server/vbot_demo.py#L626) | Give trusted service shutdown an unconditional disarm path. Invalidate the generation and cancel future cues before tearing down HTTP. Test stopping during a rest and restarting within the same process. Require an idle, disarmed controller and no later cue. |
| H3 | **Switching an Android tablet to a hosted server can leave two backends active.** Pairing saves the server and reloads the WebView. The hosted branch redirects requests and skips local boot, but the foreground service started before pairing has an independent lifecycle. The plugin exposes no stop-and-await operation for the switch. With a shared bot account, the local process can retain Lichess streams while the UI controls the hosted one. This is a source trace across React, the plugin and the service. [Pairing](src/components/TabletConnection.tsx#L21) · [Runtime selection](src/components/StandaloneRuntime.tsx#L58) · [Native interface](src/standaloneRuntime.ts#L14) | Treat backend switching as an ownership handoff. Check for an active match or robot session, end the local runtime safely, await service shutdown, then commit the new route. Exercise local → hosted → local on one device and verify there is exactly one active bot owner after each switch. |
| H4 | **A takeback can freeze the training opponent.** The bot deduplicates submissions using only the ply number. In a fake Lichess transport, Black replied to `1.e4`, accepted a takeback, observed the rewind, then sent no reply to the replacement `1.d4`. Both positions had ply 1. A duplicate snapshot of the new position also remains suppressed. [Bot submission](server/bot_runtime.py#L1124) · [Takeback tracking](server/bot_runtime.py#L1094) | Track authoritative move history and a branch generation. An accepted rewind must invalidate the old submission and takeback markers, including when the student replays the same move. Test both replay and replacement while keeping duplicate stream snapshots idempotent. |
| H5 | **A finished game can keep the bot account busy indefinitely.** The account stream’s `gameFinish` clears bookkeeping but does not retire the game worker. If the worker misses its terminal frame and receives persistent 404s when reopening the stream, it retries indefinitely. A mocked finish followed by 404s produced three reconnects with the account still busy at each retry. Switching accounts checks live worker threads. [Finish handler](server/bot_runtime.py#L928) · [Retry loop](server/bot_runtime.py#L1080) · [Busy guard](server/bot_runtime.py#L305) | Signal the worker on authoritative finish, allow a bounded final-state reconciliation, then retire it even if no final frame arrives. Keep transient reconnects for active games. Alert on a live worker for a game already marked finished. |
| H6 | **The Android pairing screen accepts the Mac launcher’s HTTP address, but the app’s network policy denies it.** The launcher publishes an HTTP LAN URL and the pairing screen uses ordinary WebView fetch. The main manifest installs a policy that permits cleartext only for loopback destinations. This blocks the advertised private-LAN path on this configuration. This finding comes from the manifest, client and Android’s documented policy. A physical tablet was not exercised. [Mac pairing URL](scripts/tablet_backend.py#L46) · [Pairing fetch](src/components/TabletConnection.tsx#L24) · [Network policy](android/app/src/main/res/xml/network_security_config.xml#L3) · [Android network security configuration](https://developer.android.com/privacy-and-security/security-config) | Make the launcher issue a trusted HTTPS URL, or implement a deliberately scoped LAN transport with an explicit security contract. Exercise a non-loopback pairing address in the Android WebView. A loopback emulator test cannot cover this path. |
| H7 | **A misconfigured hosted instance can leave operator-level chess and history APIs unprotected.** An absent or short pairing secret disables the general API gate. The backend defaults to all interfaces. The gate also exempts certain loopback requests, making protection depend on reverse-proxy topology. Bot stop, audit-log access and audit clearing are examples of affected operations. Robot and bot-account management routes have additional checks. This is a configuration and code finding. Deployment exposure was not tested. [Pairing configuration](server/tablet_access.py#L44) · [API gate](server/app.py#L2016) · [Administrative routes](server/app.py#L1873) | Make hosted mode explicit and refuse startup with invalid operator authentication. Require authorization for privileged operations independently of the proxy peer address. Run an expected-denial check through the deployed ingress and a separate authorized readiness check. |
| H8 | **The bot accepts an unconstrained challenge identifier before making a credentialed Lichess request.** Both challenge entry points reach a runtime method that checks only for a nonempty identifier, then interpolates it into the upstream request path. The server therefore cannot guarantee that the supplied value represents one challenge. The impact depends on access to the route and the bot credential’s scope. Finding established by source inspection. [HTTP entry points](server/app.py#L1916) · [Bot request construction](server/bot_runtime.py#L730) | Enforce the supported challenge-ID grammar in the shared runtime before starting the bot or making any upstream request. Cover both entry points with valid IDs and invalid-input rejection tests. |
| H9 | **One interrupted multilingual journal write can make all coaching history unreadable.** The reader decodes the whole JSONL file before its per-line recovery runs. A disposable journal containing one torn UTF-8 character between valid entries raised `UnicodeDecodeError` for game history, chat history and audit projection. Appending a valid record preserved the failure. Existing records remain on disk. [Journal reader and append recovery](server/coach/history.py#L24) | Decode and validate records independently. Preserve and flag damaged bytes while serving intact records on either side. Test a torn multibyte character, an append after restart, and retrieval of both valid records. |
| H10 | **A stale VBOT Studio tab can silently erase a saved show.** Each tab loads a snapshot, and its next library change writes the whole snapshot. Two independently loaded sessions saved different valid shows. Both saves returned success, and reloading showed only the second show. This used the production library functions and an in-memory store. [Autosave](vbot-app/src/useStudio.ts#L62) · [Library persistence](vbot-app/src/domain/library.ts#L58) | Persist shows by ID in a transaction and enforce revisions for edits to the same show. A two-tab regression should preserve independent additions and surface conflicting edits before either version is discarded. |

## Dependency monitoring

These are proposed release checks and operational signals. Monitoring cannot repair the failures above.

| Dependency | What to measure | When to act |
| --- | --- | --- |

The current health route reports HTTP 200 and `ok=true` even when engine discovery raises. [Health handler](server/app.py#L1707) · [Dependency ranges](requirements.txt) | Block promotion on startup failure, a missing engine, an illegal result or a search timeout. Use ordinary HTTP health only for process liveness. |

Track event-stream freshness, rate-limit cooldown, confirmed move submissions and game workers remaining after finish. [Native redirect](src/auth.ts#L14) · [Bot streams](server/bot_runtime.py#L803) | Investigate a failed sign-in return, a finished game retaining its worker beyond the reconciliation window, or repeated loss of the active game stream. |
| Qwen, external model providers and voice | Use a harmless short question through the selected provider. Track schema-valid answers, latency and fallback rate. Separately record voice-helper shutdown and confirmation that onboard chat was restored. Qwen’s model listing and configured flag can both succeed independently of generation. [Qwen launcher](scripts/qwen_demo_launcher.py#L35) · [Generation diagnostics](server/diagnostics.py#L209) · [Voice restoration](vbot-demo/robot_voice.py#L235) | Investigate when a configured provider returns no usable answer or fallback frequency rises. | Durable history and show storage | Track journal parse errors, size, history-read latency, write failures and conflicting saves. Rehearse a restore of saved work from an independent backup. ## Verification and scope

The audit used an archive of the checked-in revision with the local dependency installations. Both production web builds and their TypeScript checks passed. All 268 Node tests and all three mocked Qwen MCP HTTP tests passed. Python discovery covered 674 cases, including vendor serialization checks exercised with locally staged schemas. The installed Python environment passed `pip check`. A real local Stockfish process returned a legal continuation through the backend analysis function.

The robot tests used fake senders, publishers, storage and clocks. The audit exercised no live Lichess account, paid model endpoint, robot, native device or production server. Android and iOS source, the native OAuth handoff and release configurations were inspected. APK installation, iOS execution, ingress configuration, actual device motion and currently deployed versions remain unverified.

The active checkout differs from the locally recorded default branch and Android release branches. Findings apply to the SHA above. Deployment and release decisions need the candidate’s SHA, packaged assets and device-side helper version. This report contains the audit results and proposed acceptance checks. Product code and deployment configuration were unchanged.
